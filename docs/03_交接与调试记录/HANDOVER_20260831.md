## 1. 系统架构（用户 2026-08-29 拍板，勿推翻）

```
ESP32-S3-WROOM-1（无 PSRAM！DRAM ~277KB，堆 ~112KB，WiFi 后 ~17KB 可用）
  ├─ 语音：ES7210 24kHz 采集 → ai_voice_stream_record 降 16k mono
  │        → server_bridge_upload（HTTP POST 分块）→ 服务器
  │        ← 服务器回文本（上屏）+ TTS WAV（下载到 SD 播放，24kHz 直放）
  ├─ 图像：OV3660 rxbuf = RGB565 160×120（38400B 静态 DRAM 零拷贝）
  │        → server_bridge_image_analyze（HTTP POST 整帧）→ 服务器
  │        ← 服务器回诊断文本 → 诊断页上屏
  └─ 服务器地址：plant voice server <ip>（RAM 变量，重启丢失——待持久化）
        │ HTTP 明文（局域网）
        ▼
PC 端服务器 tools/server/server_bridge.py（Python 3 + requests + PIL）
  ├─ /voice/upload?session=&seq=    收 PCM 块攒 WAV（seq==0 重置会话）
  ├─ /voice/finalize?session=       WAV → MiMo mimo-v2.5 音频理解 → 文本
  │                                 → mimo-v2.5-tts → 音频（存内存待拉取）
  ├─ /voice/audio?session=          GET 返回 TTS WAV（设备边下边播）
  ├─ /image/analyze                 收 RGB565 → PIL 转 JPEG → MiMo 视觉 → 文本
  └─ /data（C1 ✅ 2026-09-03）      收任务/日记/传感器 JSON → 落盘 + MQTT 上云
        │ HTTP 明文（局域网）            │
        ▼                              ▼
   MQTT broker（云） ← 服务器 paho-mqtt 上云（E 阶段，设备零 MQTT 依赖）
```

**云同步（2026-08-31 用户定案：服务器代理上云）**：设备数据 → 局域网服务器
（已有通道）→ 服务器用 PC 端 paho-mqtt 发到云端 broker。设备**不直连 MQTT**
（无 PSRAM 下 MQTT 栈 ~10KB+ 太紧；符合"薄客户端"定案）。同步内容：传感器
数据 + AI 诊断结果 + 任务/日记（用户多选确认）。

**为什么设备不做 JPEG/OPUS**：无 PSRAM，堆小；OPUS 编码器 26KB 大块分配不出，
OV3660 切 JPEG 模式要重构 DMA（曾饿死堆）。**用带宽换内存**——raw RGB565 38.4KB、
PCM 16k 256kbps 直传，服务器做所有格式转换。这是用户定案，勿改。

## 4. 关键代码约束（改代码必读，违反会翻车）

1. **LVGL 对象只在 ui_task 操作**：worker/回调线程只能写共享缓冲 +
   标志，ui_task 定时器（500ms）消费上屏。照抄 voice 页 / camera 页模式。
2. **LCD 写屏单块宽 ≤320px**：st7789 rowbuff_be 只有 640B，整行 480px=960B
   会越界横扫 .bss（摄像头 swap 标志被毁 → 颜色错乱）。lcd_put_rgb565
   和 LVGL flush_cb 都已遵守，新写屏代码必须遵守。
3. **无 PSRAM，堆 ~17KB（WiFi 后）**：禁止 malloc 大块（>10KB 必失败）；
   语音/图像链路全部静态缓冲 + 零拷贝（borrowed 模式复用 rxbuf）。
4. **worker 线程栈 8KB**：默认 4KB 会溢出（voice/ai worker 都显式
   pthread_attr_setstacksize 8192）。
5. **页面销毁必须清理**：删定时器 + 置空静态指针 + 清 pending 标志，
   否则 use-after-free → LVGL PANIC（voice 页踩过，见 VOICE_REQUIREMENTS §9）。
6. **摄像头画面是 ioctl 直写**（绕过 LVGL）：LVGL 不认为取景框脏，
   覆盖残留要用 lcd_put_rgb565 物理填充（复用 rxbuf），不能只靠
   lv_obj_invalidate。
7. **MiMo 格式**：音频理解用 mimo-v2.5（不是 -pro），base64 必须带
   `data:audio/wav;base64,` 前缀；图像用 image_url + `data:image/jpeg;base64,`；
   TTS 返回 24kHz WAV（choices[0].message.audio.data）。max_completion_tokens
   ≥1024（300 会偶发空文本，推理 token 吃满预算）。
8. **服务器会话**：设备重启后 session 从 0 重计，服务器用 seq==0 检测
   新会话重置（勿改，改了会复现 400 风暴）。
9. **build.sh 会自动同步 defconfig→.config**（LV_MEM_SIZE 80 等），编译
   用 `./build.sh vendor/espressif/boards/esp32s3/esp32s3-box/configs/openvela/`。
10. **用户自己做编译烧录**：助手只改代码 + 提供命令，不实际编译烧录。

### 阶段 E：MQTT 云同步（2026-08-31 用户定案：数据双链路 = 本地 SD + 云端）

**用户需求**：链路数据不仅存本地 SD，还要保存到云端——传感器数据 +
AI 诊断结果 + 任务/日记（用户多选确认）。

**架构（用户拍板：服务器代理上云）**：

```
设备（薄客户端）→ 已有 HTTP 通道 → PC 服务器 → paho-mqtt → 云 broker
本地同时写 SD（双链路：SD 保底 + 云备份）
```

**为什么服务器代理而非设备直连**：
- 无 PSRAM，堆仅 ~17KB；NuttX mqttc 栈 ~10KB+ 太紧，且要处理
  掉线重连/心跳，设备负担重
- PC 端 Python paho-mqtt 成熟稳定，broker 地址/证书都在服务器侧
- 完全符合"薄客户端 + 服务器中枢"定案；设备零新增依赖

**NuttX 侧现状**：apps/netutils/mqttc（MQTT-C，TCP 明文 + mbedtls 可选）、
paho_mqtt（mqtt5）、examples/mqttc 都有；cloud_client.h 只有声明
（init/upload_sensor_data/upload_image/request_advice），**无 .c 实现**，
defconfig 未启用 —— 服务器代理方案下**设备端可完全不用这些库**，
cloud_client 保持头文件即可（或删除）。

### 阶段 F：语音降噪（用户 2026-08-31 提出交接；现状=无降噪裸跑）

**现状（代码实证）**：
- `CONFIG_PLANT_VOICE_NS` **未启用**（default n）；Makefile 走 `-DPLANT_NO_NS=1`
  分支：ai_ns.c / esp_sr shim / srmodels_data.c 全被 filter-out，**当前语音链
  无降噪裸跑**（ai_voice.c 走软件滤波链：高通220Hz→11点中值→低通5kHz→软门）。
- 根因：esp_sr NSNet2（337KB 权重）需 PSRAM，而 WROOM-1 **物理无 PSRAM**，
  `mmu_valid_space()=0` 映射失败 → ai_ns_init() 返回 <0。
- **好消息**：`ai_ns.c/h` 接口已解耦（init/process_frame/frame_size/samp_rate），
  换降噪实现**不用改调用方**（ai_voice.c 258/442/475 行）。

**方案全表（CLAUDE_SYSTEM.md §10，DRAM 余量实算）**：
基准：堆 112KB；语音会话基线 60KB（OPUS 30 + WS 15 + 环形 15）→ 余 ~52KB。

| 方案 | DRAM | 质量 | 难度 | 52KB 下可装性 | 推荐 |
|---|---|---|---|---|---|
| **① AFE 传统 NS** | <10KB | 中低 | ★ 零新增（libesp_audio_processor.a 已含）| ✅ 轻松（余 42KB）| **首选** |
| ③ SpeexDSP NS | ~5KB | 中低 | ★★ | ✅ | 备选 |
| ④ WebRTC NS | 5-10KB | 中低 | ★★★ 剥离源码 | ✅ | 备选 |
| ② NSNet1 | 40-60KB | 中高 | ★★ esp-sr 原生 | ⚠️ 极限（余 0-12KB）| Phase 2 |
| ② RNNoise | 30-50KB | 中高 | ★★★ 移植 | ⚠️ 极限 | Phase 2 |
| NSNet2 原版 | 337KB | 最高 | — | ❌ **物理不可能** | 放弃 |

**推荐路线（分两步，每步可独立验收）**：
- **F1（首选，立即做）**：开 `CONFIG_PLANT_VOICE_NS=y` + 启用 **AFE 传统 NS**
  （<10KB，esp_audio_processor.a 已链接）。改 ai_ns.c 实现从 NSNet2 换到
  传统 DSP 路径（谱减/Wiener），接口不变。验收：录音 SNR 提升、堆余量
  ≥ 40KB、不崩。
- **F2（质量升级，F1 不够再说）**：**NSNet1**（40-60KB）——esp-sr 原生轻量
  DNN，验证 `model_create` 能否在 DRAM 完成（改 heap_caps 返回 DRAM 地址）。
  验收：实时性（帧处理 < 帧时长）+ SNR ≥ 3dB + 堆余量 ≥ 10KB。

**踩坑提醒**：
- 不要碰 NSNet2 原版（337KB > DRAM 总量 277KB，物理放不下）
- esp_sr 库已全部在 `components/voice_agent/esp_sr/lib/`（libnsnet.a、
  libesp_audio_processor.a、libvadnet.a、libdl_lib.a 等），不需要重新下载
- 降噪在**服务器侧也可做**（PC 端 Python 对 WAV 降噪，设备零负担）——
  若设备端 F1 受阻，可先服务器降噪保质量，设备端降噪作为远期优化
